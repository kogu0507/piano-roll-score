# 教室専用カタログ構想

最終更新日: 2026年7月13日

この資料は、将来の有料または準有料運用として、ピアノ教室ごとに専用教材カタログを提供する案を整理するための設計メモである。

第17〜22段階で、外部/教室カタログ読み込み、教室コード入力、運用CLI、教室カタログからの直接練習導線、教材バリエーションのシリーズ表示まで実装済みである。ただし、ログイン、サーバー認証、先生用管理画面、課金処理、権利判定は未実装であり、事業化前に技術方式、運用手順、利用規約、著作権責任分界を改めて確認する。

教室へ説明するための覚書ドラフトは `docs/classroom-catalog-terms-draft.html` に置く。これは正式な契約書ではなく、申込前の確認事項を整理するためのたたき台である。

## 1. 基本方針

採用候補は次の方式とする。

- 方式A: 教室コードからハッシュ化URLを作り、教室専用カタログを読み込む。
- 教室専用カタログの教材は、教室のオリジナル教材を基本とする。
- 右手版、左手版、将来の両手版、分割練習版などは、`seriesTitle`、`part`、`variantLabel` などのカタログメタデータで同じシリーズとして整理する。
- 既存曲を使う場合は、パブリックドメインの曲だけを原則とする。
- 著作権が絡む教材データの権利確認、許諾取得、使用可否判断は、教室側または個人利用者側が行う。
- 運営側は、教材データの著作権調査、許諾取得、内容審査を原則として行わない。
- ただし、運営サーバー上にファイルを置く以上、明らかな問題、権利者からの連絡、規約違反があった場合に公開停止または削除できる権限は運営側が保持する。

この方式は、強い認証やDRMではない。合言葉または教室コードを知っている人だけが開きやすくなる簡易導線として扱う。

## 2. 想定する利用シーン

- 教室が自作した導入教材を、生徒へ簡単に配布する。
- 教室がパブリックドメイン曲を元に作った練習課題を、生徒へ配布する。
- 教室ごとに、指番号違い、左手のみ、両手、連弾プリモ、移調版などの教材を整理する。
- 運営側が制作代行したJSON教材を、教室専用カタログへ配置する。
- 教室が著作権処理済みと申告した教材を、教室専用カタログへ配置する。

## 3. 技術方式

### 3.1 教室コード

先生が生徒に伝える文字列を、教室コードまたは合言葉と呼ぶ。

例:

```text
sakura-4832
```

教室コードは、アプリ内で正規化してからハッシュ化する。

正規化の候補:

- 前後の空白を削除する
- 英字を小文字へ統一する
- 全角英数字を半角へ寄せるか、最初から半角英数字とハイフンだけを推奨する

運用を簡単にするため、初期案では教室コードは次の形式を推奨する。

```text
半角英小文字、数字、ハイフンのみ
```

### 3.2 ハッシュ化URL

アプリは教室コードからハッシュ値を作り、そのハッシュ値を含むURLのカタログJSONを読み込む。

例:

```text
教室コード:
sakura-4832

内部で作るカタログキー:
sha256("sakura-4832")

読み込み先:
https://seegmund-music-labo.com/data/piano-roll-score/classroom-catalogs/{catalogKey}/catalog.json
```

`catalogKey` は推測されにくい長い文字列になるため、通常の利用者が他教室のカタログを偶然見つける可能性を下げられる。

ただし、コードやURLが漏れた場合はアクセス可能になる。認証ではないため、秘密性が必要なデータや権利上の不安があるデータを置かない。

### 3.3 カタログと楽曲JSONの配置例

```text
/data/piano-roll-score/classroom-catalogs/
  {catalogKey}/
    catalog.json
    songs/
      001.json
      002.json
      left-hand-001.json
```

アプリ本体とは別に、データ配信用ディレクトリへ置く想定である。

```text
/app/piano-roll-score/
  アプリ本体

/data/piano-roll-score/classroom-catalogs/
  教室専用カタログと曲データ
```

同一ドメイン配下であれば、通常はCORS設定なしで読み込める。

## 4. 教室専用カタログJSON案

最初の形式案は次のとおり。

```json
{
  "schemaVersion": 1,
  "catalogType": "classroom",
  "classroom": {
    "displayName": "さくらピアノ教室",
    "catalogName": "導入教材",
    "updatedAt": "2026-07-09"
  },
  "songs": [
    {
      "id": "001",
      "title": "メリーさんの羊",
      "description": "右手導入用",
      "level": "導入",
      "catalogGroup": "右手",
      "songUrl": "./songs/001.json"
    },
    {
      "id": "left-001",
      "title": "メリーさんの羊 左手",
      "description": "左手のみの練習",
      "level": "導入",
      "catalogGroup": "左手",
      "songUrl": "./songs/left-001.json"
    }
  ]
}
```

`songUrl` は、カタログJSONから見た相対URLを基本とする。外部URLも将来対応できるが、初期運用では同じ教室カタログ配下に置く方が安全で管理しやすい。

## 5. アプリ側の想定UI

ホーム画面に、教室専用カタログへの導線を追加する。

```text
ホーム
├─ 曲を選ぶ
├─ ピアノ表示 / スコア表示
├─ 曲カタログ
└─ 教室コード
   ├─ 入力欄
   └─ 教室カタログを開く
```

教室コードが正しければ、教室専用カタログを表示する。間違っている場合は、「カタログが見つかりません」と表示する。

初期実装では、教室カタログをアプリ本体のホーム曲セレクターへ混ぜる必要はない。まずは専用カタログ画面を開き、そこから教材を選ぶ形がよい。

第20段階では、教室利用時の階層を浅くするため、教室カタログの各曲カードに次の直接練習ボタンを置いた。

```text
曲カード
├─ 曲名、説明、グループ、level
├─ ピアノ表示
├─ スコア表示
└─ JSONを確認
```

`ピアノ表示` と `スコア表示` は、該当 `songUrl` の曲JSONを読み込み、既存の楽曲スキーマ検証に通したうえで、そのまま練習画面へ進む。`JSONを確認` は、教材JSONを確認したい利用者や運用担当者向けの補助導線として扱う。

## 6. セキュリティ上の扱い

この方式は、次を目的とする。

- 生徒が教室コードで教材へ到達しやすくする。
- 関係ない利用者が偶然カタログを見つけにくくする。
- サーバー認証なしで、静的ホスティングのまま運用する。

この方式が保証しないこと:

- 契約者だけが必ず見られること
- 生徒が他人へコードやURLを共有できないこと
- 教材データをコピーされないこと
- 著作権侵害リスクを技術的に防ぐこと

そのため、次のデータは置かない。

- 秘密情報
- 生徒の個人情報
- 権利処理に不安がある曲
- 市販楽譜の丸写し
- 歌詞データ
- 教室が権利を確認していない教材

## 7. 著作権責任分界

基本方針:

- 運営は教材データの著作権調査、許諾取得、利用可否判断を行わない。
- 教室がアップロードまたは掲載依頼する教材について、必要な権利確認は教室側が行う。
- 個人利用者が自分でJSONを読み込む場合、そのデータの扱いは個人利用者が管理する。
- 運営は、教室から受け取ったデータを指定の場所へ置くホスティング補助またはデータ配置補助を行う立場とする。

ただし、運営サーバー上にデータを置く以上、運営は次の権限を持つべきである。

- 権利者または第三者から問題を指摘されたデータの公開停止
- 規約違反が疑われるデータの一時停止
- 教室との契約終了時のデータ削除
- 明らかに不適切な教材の掲載拒否

契約または申込時に、最低限次を確認する。

- 掲載する教材は教室のオリジナル、パブリックドメイン曲に基づくもの、または教室側で権利処理済みである。
- 市販楽譜、教材本、他者制作データを無断で転記しない。
- 歌詞は原則として掲載しない。
- 権利者から問い合わせがあった場合、教室側が必要な説明と対応を行う。
- 運営は問題があると判断したデータを停止できる。

## 8. 事業化の単位

料金化する場合は、機能を分けて考える。

### 8.1 教室専用カタログ枠

教室ごとに、静的カタログ置き場を提供する。

課金単位の候補:

- 月額
- 年額
- 曲数上限
- データ容量上限

### 8.2 JSON教材制作代行

先生が作りたい教材を、運営側がJSON化する。

これは技術的にも教育的にも価値が大きい。先生側が最も詰まりやすいのはJSON制作であるため、アプリ利用料よりも制作代行の方が収益化しやすい可能性がある。

### 8.3 PD教材パック

運営側が、パブリックドメイン曲やスケール練習を教材化したサンプル集を提供する。

これは営業用にも有効である。

- 体験レッスン用
- 右手導入
- 左手導入
- 両手導入
- 移調練習
- 連弾プリモ

## 11. 現時点の推奨

すぐにログインやサーバー認証を作らない。

まずは、静的ホスティングのまま次を目指す。

```text
教室コード
→ ハッシュ化URL
→ 教室専用catalog.json
→ 教室専用教材を開く
```

著作権面では、運営は権利処理を代行しない。掲載データの権利確認は教室側が行い、運営は問題発生時の停止権限だけを持つ。

この形なら、現在の静的アプリ構成を大きく壊さず、教室ごとの教材配信と有料運用の可能性を検証できる。
## 11. 第17段階で実装した範囲

第17段階では、教室コード入力やハッシュ化URLは実装せず、運用確認用の基盤として次だけを実装した。

- ホーム画面の「データ管理」内で、任意の `catalog.json` URLを入力して読み込む。
- 教室カタログJSONは `schemaVersion: 1`、`catalogType: "classroom"`、`classroom.displayName`、`classroom.catalogName`、`songs` を必須とする。
- 各曲は `id`、`title`、`songUrl` を必須とし、`description`、`level`、`catalogGroup` を任意とする。
- `songUrl` はカタログURLから見た相対URLとして解決する。
- `javascript:`、`data:`、`file:` は拒否し、初期実装では `http:` / `https:` / 同一origin相対URLを許可する。
- 読み込んだカタログは1列カードで表示し、曲カードから既存のピアノ表示・スコア表示へ進める。
- 開発確認用カタログとして `public/data/classroom-catalogs/demo/catalog.json` を追加する。
- `?catalog=...` で初期読み込みできるようにする。

未実装として残すもの:

- 教室コード入力
- 教室コードの正規化とハッシュ化
- 本番用 `/data/piano-roll-score/classroom-catalogs/{hash}/...` への固定
- ログイン、サーバー認証、クラウド同期
- 先生用管理画面
- 権利判定や公開停止フローの画面実装

## 12. 第18段階で実装した入口

第18段階では、アプリ側の入口として次を実装した。

- ホーム画面の「データ管理」内に「教室コードで開く」を追加した。
- 教室コードは前後空白削除、英字小文字化、代表的な全角英数字・ハイフン類の半角化を行い、半角英小文字、数字、ハイフンだけを許可する。
- 正規化済み教室コードをSHA-256でハッシュ化し、`/data/piano-roll-score/classroom-catalogs/{hash}/catalog.json` を作る。
- 開発確認用の `demo` だけ、アプリ同梱デモカタログへマップする。
- `?classroom=demo` で初期読み込みできる。
- 読み込んだ教室カタログは、教室名、カタログ名、更新日、ホームへ戻る操作、グループ別1列カードを持つアプリ内画面として表示する。

未実装として残すもの:

- ログイン、サーバー認証、教室コードのサーバー照合
- 教室コード履歴保存、最近使った教室、お気に入り
- 教室カタログの検索・フィルター
- 先生用管理画面
- 教材の権利確認フロー、契約終了時の公開停止運用

## 13. 第19段階で実装した運用ツール

第19段階では、教室専用カタログを実際に作るための運用CLIと手順を追加した。

- `npm.cmd run classroom:hash -- <教室コード>` で、正規化済みコード、SHA-256のcatalogKey、本番想定URLパスを確認する。
- `npm.cmd run classroom:scaffold -- --code ... --name ... --catalog ... --out ...` で、明示した出力先へ `{catalogKey}/catalog.json` と `songs/README.md` の雛形を作る。
- `npm.cmd run classroom:validate -- <catalog.json>` で、教室カタログスキーマ、危険な `songUrl`、同一教室フォルダ配下の曲JSON存在、既存楽曲スキーマを検証する。
- 運用手順を `docs/classroom-catalog-operations.md` にまとめた。

第19段階の重要な判断:

- 教室専用データはアプリ本体の `public/` ではなく、サイト側 `/data/piano-roll-score/classroom-catalogs/{catalogKey}/` に置く。
- 雛形作成直後の `songs: []` は有効な教室カタログとして扱う。
- CLIは本番運用向けにcatalogKeyを確認するため、アプリ画面側の `demo` 特別マップは適用しない。
- カタログ上の `songs[].id` と曲JSON内の `id` は一致必須にしない。ただし運用上は一致を推奨する。

未実装として残すもの:

- アプリ画面上の先生用管理UI
- ブラウザ上の教室カタログ編集
- 自動FTPアップロード
- サーバー認証、ログイン、クラウド同期
- 教室コード履歴保存、最近使った教室、お気に入り
- 教材の権利確認フローの自動化
