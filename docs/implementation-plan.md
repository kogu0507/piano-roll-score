## 4. 第7段階の目的

第7段階の目的は、視覚的な再生に拍の音を加え、利用者が入るタイミングを取りやすくすることである。

具体的には次を実現する。

- メトロノームON/OFFを切り替えられる。
- 1拍目は高い音、その他の拍は低い音にする。
- メトロノーム音量を調整できる。
- 再生速度変更にメトロノーム音も追従する。
- プリカウントを「なし」「1小節」「2小節」から選べる。
- プリカウント中は譜面を進めず、カウント後に既存の再生を開始する。
- 縦表示と横表示のどちらでも同じメトロノーム・プリカウント設定を使う。

## 5. Web Audio APIの扱い

### 5.1 初期化

- AudioContextは、利用者の操作後に初期化または `resume()` する。
- ページ表示時に自動で音を鳴らそうとしない。
- ブラウザの自動再生制限によりAudioContextが `suspended` になる場合を想定する。
- 音を開始できない場合は、画面が壊れないようにし、可能なら「もう一度スタートを押してください」程度の回復可能な案内にする。

### 5.2 音の作り方

- 外部音源ファイルは使わず、Web Audio APIの `OscillatorNode` と `GainNode` などで短いクリック音を生成する。
- 1拍目は高い音、その他の拍は低い音にする。
- 音は短く、長く残らないようにする。
- 音量は0から100%相当の範囲で調整できるようにする。
- 音量の初期値は大きすぎない値にする。推奨は50%から60%程度である。

### 5.3 スケジューリング

- メトロノームは `requestAnimationFrame` だけに依存しない。
- Web Audio APIの時刻を使い、可能な範囲で少し先の拍をスケジュールする。
- 先読み幅、タイマー間隔などの実装値は、テストしやすい小さな関数として分離する。
- 再生、一時停止、先頭に戻す、シーク、再生速度変更、タブ非表示に追従して、不要な予約音が鳴り続けないようにする。

## 6. プリカウント仕様

### 6.1 選択肢

プリカウントは次の3択とする。

- なし
- 1小節
- 2小節

この段階では設定を永続保存しない。永続保存は第8段階で扱う。

### 6.2 小節数と拍数

- 1小節あたりの拍数は、楽曲データの `timeSignature.numerator` を基準にする。
- 現在のデータ形式では音符の `time` と `duration` は拍単位で扱っているため、4/4なら1小節は4拍、3/4なら1小節は3拍として扱う。
- `timeSignature.denominator` は表示上の拍子情報として保持するが、第7段階のプリカウント長計算では `numerator` を基準にする。

### 6.3 開始時の挙動

- 停止中または終了後に「スタート」を押したとき、プリカウントが「1小節」または「2小節」なら、まずプリカウント状態へ入る。
- プリカウント中は `currentBeat` を進めない。
- プリカウントが終わったら、プリカウント開始前の `currentBeat` から再生を開始する。
- 一時停止からの再開では、原則としてプリカウントを挟まず、その位置から再開する。停止中から始めるときだけプリカウントを使う。
- 「先頭に戻す」を押した後は停止状態なので、次のスタートではプリカウント対象になる。

### 6.4 プリカウント中のUI

- 状態表示に「プリカウント中」と分かる表示を出す。
- 可能であれば、現在のカウント拍を表示する。
- プリカウント中に一時停止または先頭に戻す操作をした場合は、プリカウントをキャンセルする。
- プリカウント中に縦横表示を切り替えても、アプリが壊れないようにする。可能な範囲でプリカウント状態を維持するが、実装上難しい場合は安全に停止してよい。その場合は完了報告に判断を記載する。

## 8. 既存機能との関係

維持すること:

- 縦表示と横表示の共通 `currentBeat`
- スタート、一時停止、先頭に戻す、シーク、再生速度変更
- 縦表示で音符が上から下へ流れること
- 横表示で音符が右から左へ流れること
- 縦横切り替え時の現在位置維持
- タブ非表示時の自動一時停止
- 縦表示の白鍵幅調整と横位置調整
- 横表示の五線間隔調整と譜面縦位置調整
- ロード画面へ戻ったときのJSONと検証結果保持
- C♯とD♭の扱い
- 高DPI Canvas、リサイズ、端末回転対応
- ページ全体に横スクロールを発生させないこと

壊してはいけない分離:

- シークは曲の現在位置を変える操作である。
- 縦表示の白鍵幅・横位置調整は表示調整である。
- 横表示の五線間隔・譜面縦位置調整は表示調整である。
- メトロノームとプリカウントは再生補助であり、音符のピアノ音源再生ではない。

## 18. 第8段階 端末内保存と設定保存

### 18.1 目的

第8段階の目的は、利用者が明示的に保存した楽曲を端末内へ保存し、表示・再生設定を次回起動時に復元できるようにすることである。

この段階の保存は、クラウド保存ではない。その端末の、そのブラウザ内だけで使える保存である。ユーザー登録、ログイン、クラウド同期、外部サーバー保存は扱わない。

### 18.2 保存対象

楽曲データ:

- 利用者が明示的に保存操作をした検証済み楽曲をIndexedDBへ保存する。
- 読み込んだだけの内蔵曲、URL曲、貼り付けJSON、JSONファイルを自動保存しない。
- 保存時には曲名、保存日時、更新日時、保存IDを保持する。
- 保存データは、既存の楽曲スキーマと同じ検証フローで読み込む。
- 保存データが壊れている場合は、アプリ全体を止めず、回復可能なエラーとして表示する。

設定:

- 小さな設定値は `localStorage` へ保存する。
- 縦表示の白鍵幅と横位置を保存する。
- 縦表示の調整値は、可能であれば端末の縦向きと横向きで分けて保存する。
- 横表示の五線間隔と譜面縦位置を保存する。
- 再生速度、メトロノームON/OFF、メトロノーム音量、プリカウント設定を保存する。
- 壊れた設定値、範囲外の設定値、古い形式の設定値があっても、初期値へ戻してアプリを継続する。

### 18.3 UI要件

- ロード画面または楽曲画面から、現在の検証済み楽曲を端末内へ保存できる。
- 保存一覧を表示できる。
- 保存一覧には、曲名、保存日時または更新日時を表示する。
- 保存一覧から読み込める。
- 保存一覧から削除できる。
- 削除時は確認を出し、キャンセルできるようにする。
- 保存データがない場合は、空の状態を分かりやすく表示する。
- 「この端末のこのブラウザ内だけに保存され、別端末には同期されない」ことを画面上で明示する。
- ブラウザのデータ削除で消える可能性があるため、重要なデータにはJSON書き出しを案内する。
- 既存のJSON書き出し機能を壊さない。

### 18.4 設計方針

- IndexedDB操作は、DOMやCanvasから分離する。
- `localStorage` 操作は、設定の正規化と分離する。
- 保存形式にはバージョンを持たせる。
- 将来のスキーマ移行に備えて、保存レコードの型を明確にする。
- JSON由来、保存データ由来の文字列を `innerHTML` へ直接入れない。
- 保存一覧の操作は、既存の共通検証フローへ接続する。
- 保存処理が失敗した場合は、ユーザーに分かるエラーを表示する。
- プライベートブラウズや容量制限などで保存できない場合を想定する。

- storageId
- songId

- updatedAt
- song

## 19. 第9段階 レスポンシブ対応と操作性調整

### 19.1 目的

- フォーカス表示を消さない。
- 色だけで状態を判断させない。必要な状態は文言でも示す。
- ノッチやホームインジケーターの安全領域を極端に侵さない。

## 28. 第15段階 アウフタクト対応

### 28.1 目的

第15段階の目的は、「聖者の行進」など曲頭が弱起で始まる教材を、データ作成者とAIが見直しやすい形で扱えるようにすることである。教育用アプリではアウフタクトのように拍を取りにくい曲ほど専用教材として増える可能性があるため、曲データが増える前に正式な扱いを定める。

### 28.2 採用するデータ方針

- 楽曲全体に任意項目 `pickupBeats` を追加する。
- `pickupBeats` はアウフタクトの長さを拍単位で表す。省略時は `0` とする。
- `pickupBeats` は `0` 以上、`timeSignature.numerator` 未満とする。
- `pickupBeats: 0` の曲では、従来どおり `note.time` は0以上とする。
- `pickupBeats > 0` の曲では、`note.time` に `-pickupBeats` 以上の負数を許可する。
- JSON上の `time: 0` は、常に1小節目1拍目を意味する。
- アウフタクト部分は、`-pickupBeats` 以上0未満の `time` で表す。
- アプリ内部では、`playbackTime = note.time + pickupBeats` へ正規化して、再生開始からの0以上の時刻として使う。
- 拍線、小節線、メトロノームの拍位置や強拍判定では、`scoreTime = playbackTime - pickupBeats` を基準にする。
- `pickupBeats` が半拍を含む場合でも、メトロノームのクリック位置は `playbackTime` の整数ではなく、`scoreTime` の整数位置に合わせる。

4/4拍子で八分音符3つ分、つまり1.5拍のアウフタクトがある場合は、次のように書く。

```json
{
  "timeSignature": {
    "numerator": 4,
    "denominator": 4
  },
  "pickupBeats": 1.5,
  "notes": [
    { "id": "p1", "time": -1.5, "duration": 0.5 },
    { "id": "p2", "time": -1.0, "duration": 0.5 },
    { "id": "p3", "time": -0.5, "duration": 0.5 },
    { "id": "m1", "time": 0.0, "duration": 1.0 }
  ]
}
```

### 28.3 実装対象

- `schemaVersion: 1` のまま、後方互換の任意項目として `pickupBeats` を追加する。
- 楽曲検証で、`pickupBeats` の範囲と、各音符の `time >= -pickupBeats` を確認する。
- 再生・描画で使う内部時刻を正規化する処理を、DOMやCanvasから分離した純粋関数として追加する。
- 曲の長さ計算は、正規化後の再生時刻で扱う。
- ピアノ表示とスコア表示の音符位置、拍線、小節線、シーク、再生ガイド、プリカウント助走表示が、正規化時刻に基づいて自然に見えるようにする。
- 拍線・小節線は、JSON上の `time: 0` を1小節目1拍目として扱う。
- メトロノームのクリック位置と強拍は、`scoreTime` を基準にする。1小節目1拍目、つまりJSON上の `time: 0` でアクセントが鳴るようにする。
- プリカウントは、アウフタクト開始へ入るための助走として扱う。プリカウント後はアウフタクト部分から再生が始まる。
- アウフタクト曲の内蔵サンプルを1曲追加する。候補は「聖者の行進」など、曲頭が弱起であることが分かりやすい短い練習曲とする。
- `catalog.html`、`index.json`、関連テストを更新する。

### 28.5 完了条件

1. `pickupBeats` なし、または `0` の既存曲が従来どおり動く。

## 31. 履歴: 第7.5段階 再生ガイドと助走表示

### 25.1 目的

第7.5段階の目的は、アプリの見え方を音楽ゲーム的な「判定線へ完全一致させる」ものから、教育用の「テンポと譜面の流れをつかむ」ものへ寄せることである。

### 25.2 実装方針

- 「判定ライン」というUI文言を「再生ガイド」へ変更する。
- 赤い強い線ではなく、薄い線または半透明の帯として表示する。
- 縦表示と横表示の両方で同じ方針にする。
- プリカウント中も、表示用の助走位置で譜面を流す。
- 実際の `currentBeat` はプリカウント中に進めない。
- Canvas描画には、実再生位置とは別の `displayBeat`、`renderBeat`、または同等の表示用拍位置を渡せるようにする。
- プリカウント終了後は、表示用拍位置と実際の `currentBeat` が自然につながるようにする。
- シーク、現在位置表示、保存対象の再生位置は、実際の `currentBeat` を基準にする。

### 25.3 助走表示の考え方

プリカウント中の表示用拍位置は、次のような考え方を基準とする。

```text
displayBeat = currentBeat - precountRemainingBeats
```

たとえば、4/4で1小節プリカウントの場合は、開始時に `displayBeat = -4` として描画し、カウントが進むにつれて `displayBeat` が0へ近づく。これにより、1拍目から突然画面が動き出すのではなく、テンポに合わせて譜面が先に流れ始める。

実装上より自然な計算があれば調整してよい。ただし、プリカウント中に利用者へ表示する「曲の現在位置」は、0拍または開始前であることが分かる表示にする。
