# プロジェクト進行表

## 1. この資料の目的

この資料は、`piano-roll-score` の全体進行をユーザーとCodexが共有するための一覧である。

次の疑問に答えることを目的とする。

- 今どの段階にいるか
- 次に何を実装するか
- 実装スレッドへ何を依頼するか
- 実装完了後にユーザーが何をすればよいか
- どの時点で設計判断や手動確認が必要か

詳細な製品仕様は `spec.md`、現在の実装段階の詳しい作業内容は `docs/implementation-plan.md` を参照する。

## 2. 資料の使い分け

| 資料 | 役割 |
|---|---|
| `spec.md` | 何を作るか、なぜ作るかを定める |
| `AGENTS.md` | Codexが守る作業ルールを定める |
| `docs/project-roadmap.md` | 全体の順序、進捗、ユーザーの次の行動を示す |
| `docs/implementation-plan.md` | 現在の実装段階の詳細と完了条件を示す |
| `README.md` | プロジェクトへの入口と開発方法を示す |

## 3. 進行管理の方法

各段階は次の順序で進める。

1. 設計スレッドが、次の段階の範囲と実装指示を作る。
2. ユーザーが、その指示を実装スレッドへ渡す。
3. 実装スレッドが、実装、テスト、ビルドを行う。
4. ユーザーが、実装スレッドの完了報告を設計スレッドへ共有する。
5. 設計スレッドが、結果、未決事項、次の段階を確認する。
6. 必要な場合だけ、ユーザーが実機またはブラウザで手動確認する。
7. 設計スレッドが資料を更新し、次の実装指示を作る。

ユーザーは、技術的な判断やコマンド実行を自分だけで行う必要はない。必要な操作がある場合は、設計スレッドが目的、手順、正常な結果、問題が起きた場合の対応を具体的に案内する。

- セーフエリア
- アクセシビリティ

想定するユーザー確認:

- 実際に利用予定の端末で操作できるか
- ボタンが小さすぎないか
- 画面回転後も使えるか

### 第10段階: 教室での手動検証とMVP仕上げ

状態: 未着手

主な内容:

- 手動テスト
- 教育実験記録
- 不具合修正
- 説明文の改善
- MVP完成条件の確認

ユーザーが行う予定の内容:

- 先生と試用する
- 子供または初心者の反応を記録する
- 技術的な不具合と教育上の改善案を分けて報告する

## 7. 実装スレッドから報告を受け取ったとき

ユーザーは、実装スレッドの報告内容を完全に理解してから共有する必要はない。

次のような技術用語が含まれていても、そのまま設計スレッドへ貼り付けてよい。

- typecheck
- unit test
- E2E
- build
- dependency
- Vite base
- Playwright browser
- warning
- skipped

設計スレッドが内容を整理し、次を日本語で説明する。

- 予定どおり完了したか
- 問題があるか
- ユーザーによる確認が必要か
- 次に実装スレッドへ何を依頼するか

## 8. 各段階で設計スレッドが提供するもの

設計スレッドは、各段階の開始時に必ず次を提供する。

### 実装スレッド向け

- コピーして送れる実装指示
- 作業範囲
- 実装しない項目
- 完了条件
- 必要なテスト

### ユーザー向け

- 今回何が追加されるか
- ユーザーが今すること
- 作業中に質問された場合の対応
- 完了後に確認する内容
- 操作手順
- 正常な状態
- 問題が起きた場合に共有する情報

ユーザー向けの説明は、ソフトウェア開発の初心者を前提とし、コマンド名だけを示して終わらせない。

## 9. 状態の表記

各段階の状態は次のいずれかとする。

- 未着手
- 指示準備中
- 実装開始待ち
- 実装スレッドで作業中
- 設計スレッドで確認中
- ユーザー確認待ち
- 修正中
- 完了
- 保留

状態変更は設計スレッドがこの資料へ反映する。
